# 對外發文專項：release notes 和推文

## 推文 / 社交發文五規則

適用於已有社群語氣和輕量釋出節奏的產品工程師專案對外發文：

1. **社群先行**：開頭用社會錨點（star 數、感謝使用者、誰的回饋推動了這次修復）。改動清單跟在後面，不放在最前。
2. **亮點不全量**：挑 2 到 4 個最有意思的改動。跳過整個模組也沒問題。讀者要的是故事，不是 changelog。
3. **使用者感受幀**：每條寫法用"你用它的時候…"或"有一種…的感覺"，不是"這個工具做了…"。
4. **一條立場**：至少一句表明決策原因的意見句（例："我更相信模型本身的能力，而非各種規則限制他的天花板"）。
5. **中文節奏**：用地道表達（給留了一手、玩玩、大夥、大概就是這些）。避免翻譯腔和正式詞（具體判據、主軸、本意）。

結尾用邀請，不用 CTA：「假如沒有用過的小夥伴，歡迎去試試看，玩玩。」而不是「立即升級」。

## Release Notes 格式

**結構**：Breaking Changes → New Features → Fixes & Improvements → Deprecations

**格式**：優先匹配目標專案最近一次 release。沒有可用參考時，使用編號列表、bold 標籤、一句話說使用者效果；只有目標專案已經使用中英雙語時才輸出雙語。

**長度參考**：和上一個版本 release 的條目數、句子長度、密度匹配。不要自創新格式。

**邊界**：GitHub Release 正文和社交公告是兩份 artifact。Release notes 解釋使用者會感受到什麼，預設不寫 CI、tap、registry、API 名稱、fallback 路徑等機制細節；公告另按社交發文規則挑 2 到 4 個亮點。

## 對外發文專項檢查

公開發文交出去之前，掃三件事：

**1. 身份和敏感訊號脫敏**：不出現可反推作者身份的細節（僱主、地點、履歷式表述）。技術決策可以具體，身份資訊預設刪。

**2. 不踩競品**：介紹自己產品時不主動貶低同類產品。直接說自己做了什麼、為什麼。

**3. 使用者感受先於功能清單**：先給一句場景或感受，再進改動細節。不要開場就列功能。

## 發版前檢查

- 不出現"不再更新"、"final release"、"停止維護"等終止訊號（除非是真實情況）
- release title 簡潔：版本號 + 最核心的改動或主題，不超過 10 個詞
- 中英版本條目數一一對應
- 建議 5 到 8 條，每條一句話
