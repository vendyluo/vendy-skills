> **怎麼用這份檔案**：它是「認 AI 味」的例子庫，不是從頭套到尾的檢查清單。先用它識味，再憑判斷改。自然的句子就別動，**過度改和改不到位一樣糟**。作者已有的聲音、口語詞和體裁選擇，優先於任何單條規則。下面所有停用詞、替換表、形式規則（標題、列表、標點），都是「傾向和例子」，不是查詢替換。沉澱新教訓時並進已有原則，別再加一條停用詞，這份檔案不許只增不減。

## 中文場景

像資深工程師寫技術長文，給同行講清楚一條鏈路。自然、準確、不刻意。

### 執行流程（先後順序）

按下面順序改，不要反著來：

1. 先保語義：先確認事實、邏輯、因果都不變。
2. 再去 AI 味：刪模板句、刪講解腔、刪報告腔。**首先檢查段末收尾總結句**（"這說明"、"到這裡"、"可以看出"開頭的重述句），這是最高頻的 AI 痕跡，優先刪。
3. 再順句子：解決拗口、斷句過碎、節奏太硬。
4. 最後調標點：減少不必要的括號、引號和短句句號連發。
5. 術語只在必要處解釋：首次出現可註解，後文不重複堆註釋。
6. 全文回讀一次：優先改卡頓點，不為“更口語”硬改自然句。

### 最高優先順序：自然 > 風格化

不要為了”像人說話”硬塞口語詞、情緒詞、俚語、感嘆詞。
一句話如果已經自然、清楚、穩，就不要再往裡加”其實 / 說白了 / 哈哈 / 誰能想到 / 我去 / 居然 / 太太太”這類詞。

**保留作者已用的口語詞**：如果作者原文已經在用”很”、”其實”、”到底”這類自然詞，不要替換成正式詞。”最高優先順序”是不要主動新增，不是要替換掉已有的。過度去口語化和過度口語化一樣糟糕。

### 預設模式：技術長文

目標不是”更隨便”，而是”更自然、更穩”。讀起來像人寫的，不是像報告，也不是像刻意模仿語音轉文字。
技術文預設是工程師對工程師，不是老師訓人。少用命令式句子、審問式起手和居高臨下語氣。

- 可以口語，但不要俚語化
- 減少情緒詞、感嘆詞、口頭禪
- 少用”說白了 / 其實 / 你會發現 / 誰能想到”這類推進詞
- 優先追求：清楚、穩、具體、節奏自然
- 不要為了去 AI 味，把技術文改得像口播稿
- 如果原句已經自然、準確、清楚，不要為了”更像人”繼續改
- 優先做減法：刪解釋腔、刪總結腔、刪多餘轉折，不要把潤色做成重寫

**受眾非工程師時的調整**：如果文章定位是產品 / 業務 / 運營受眾，先去三類詞：俯視詞（"不懂技術的同學"）、命令腔（"你必須 / 一定要"）、過深術語（"原語 / 未命中 / 非工程團隊"）。prose 走"我怎麼用，你跟著試"路徑，不要"系統梳理 + 框架表格 + 長段分析"。

### 開頭直接

NO: 隨著...的發展
OK: 用了不到一個月後
OK: 作為長期使用者，我更關心...
OK: 這次想把 X 這條鏈路講清楚
OK: 先說結論，再展開過程

### 用詞去正式化

| NO: 不用 | OK: 用 |
|---------|------|
| 非常 / 極其 | 很 |
| 值得注意的是 | 直接說結論 |
| 綜上所述 | 直接收尾 |
| 例如 | 比如 |
| 購買 | 買 |
| 使用 | 用 |
| 很多同學 / 不少同學 | 很多人 / 不少人 |
| 這幾個事 | 這幾件事 |

### 口語詞慎用，不要靠它們製造“人味”

下面這些詞不是停用，但預設不要主動加進去：

- 太太太
- 居然
- 誰能想到
- 於是乎
- 我去
- 哈哈

`好比` 只在比喻真的有幫助時偶爾用一次，不要當成固定連線詞。

### 生動化：只在原句讀不懂時才換

預設不改。只有原句抽象到讀者看不懂意思時，才換成更具體的表達。已經清楚的句子不要為”更形象”硬改。

| NO: 過度形象化 | OK: 保持原句或微調 |
|---------|--------|
| 都在偷你的上下文空間 | 都是上下文成本（原句已經清楚） |
| 絕對不能幹的事 | 禁止事項（技術文不需要這種語氣） |
| 說白了，[結論] | 直接寫結論，不加口語引導 |
| X 就是”你怎麼知道做對了”這個問題的答案 | 從問題或場景出發描述 X |
| 這就是 X 的力量 | 刪掉，讓事實說話 |

### 句式

- 不用"首先...其次...最後"，用"一方面...另一方面..."
- 段落可以長，但要一口氣能讀完
- 不用強行斷句
- 單獨成段的一兩句話，多半是上一段的收尾或下一段的引子，直接並進去，別讓它孤零零
- 四五個句號連發、每句都很短，讀起來像在打電報，這時候把幾句合成一個長句，或者用逗號連起來
- 少用“先問問是不是 X”“你得先明白”這類起手，容易有訓人感，改成“可以先看 X”“先確認 X”
- 分析型技術文裡，少用“第一、第二、第三”模板，除非在寫操作步驟
- 三個承重點如果關係很緊，優先寫成一段自然段，不必強行拆成列表

### bold 起手 + 句號 節奏

`**xxx**。content` 這種「小標題 + 句號 + 解釋」起手段落是 AI 模板感的高頻源，**不論密度，預設換成 `**xxx**，content`**，讓 bold 變成句子的承重詞，而不是獨立小標題。整段讀起來是 prose，不是工整 bold 列表。

```
NO: **alias**。我在 .zshrc 里加了一行...
OK: **alias**，我在 .zshrc 里加了一行...
```

例外：`**xxx**` 本身就是一個完整句子（如「**能跑不代表安全**」、「**準不準才重要**」），後面跟句號是正常句子結束，不屬於"小標題"模式，保留。

判斷訊號：bold 部分單獨看是不是一個能獨立成立的句子。是 → 句號；不是（只是個標籤 / 短語 / 名詞）→ 逗號。

### 列表去 list 化的漸進策略

技術長文裡 bullet 列表過多會顯得像 PPT。從 list 走到 prose 的漸進路徑：

1. 序號列表 1/2/3 → 改 bullets `- xxx`（去掉序號感）
2. bullets `- **xxx**：content` → 改 bold 段落 `**xxx**，content`（去掉 list marker）
3. 4+ 個 bold 段落 → 合成一個 prose 段落，每項用分號串起來（去掉 visual 切片感）

中間停在哪一步都行，不必一步到底。判斷訊號：

- 每條都有大段獨立解釋 → 適合 bold 段落
- 每條 1 句話，關係緊密 → 適合 inline prose 串起來
- 每條是平行規則、讀者要掃一眼對照 → 保留 bullets 也行
- 章節標題已經把列表的總結寫出來了 → 內容部分儘量 prose 化

序號 1/2/3 留給真正有順序的：優先順序、時間、流程步驟、reference 排序。

預設傾向：判斷 / 取捨 / 總結型清單（每條一句、是觀點不是步驟）預設轉成 prose 段落；速查表 / syllabus（術語密集、讀者要逐項對照）和帶連結的參考文獻保留 list。拿不準時，先轉 prose 看讀不讀得順。

### 結構級重複與表格復讀（長文專項）

後面 AI 味檢測第 3 條「重複核心觀點」是段落級。長文還有三類只有把整篇攤開橫向比對才看得到的結構水分，單段 in-place 潤色檢測不到：

- **跨章節同義清單**：同一張評估 / 判斷 / 取捨清單在 2+ 個 `##` 節裡各寫一遍（比如「評估機器人看動作頻率、資料來源、失敗處理」在入門、對比、總結三處都出現）。留資訊最全的一份，其餘刪，或後文一句話帶過。
- **表格旁正文復讀**：一節裡有對比表，正文卻一行行復述表裡的列。正文只補表給不了的，里程碑、具體例子、判斷、為什麼，表能講清的交給表。
- **圖 / 表旁文字複述**：緊鄰一張圖或表的正文，把圖 / 表已經列出的項再用文字列一遍，或用「這張圖更直觀」這類預判句替圖說話。刪掉複述和預判，留判斷和上下文；畫圖過程只在它本身是敘事時才保留。例外：圖的 alt 讀者看不到，「圖後必要說明段」不算復讀，不要刪（見圖片節奏）。

判斷訊號：刪掉這段 / 這句，讀者會不會丟失一個別處沒有的事實，不會就是復讀，刪；會就保留。

### 標題設計

標題格式三種，看結構選，不是統一用一種。

**冒號格式**（主題：補充說明）適合：術語首次出現需要解釋（ACI：工具是給 Agent 的互動介面）、主題加原則性結論（安全沙箱：邊界比功能重要）。

**一句話格式**適合：副標題只是弱標註、沒什麼資訊量；兩部分讀起來斷裂感強；副標題和主標題意思重複。

NO: 幻覺放大：多 Agent 特有的坑（"特有的坑"是弱標註，刪掉資訊量不變）
OK: 多 Agent 下幻覺會互相放大

NO: 長程任務：跨上下文的工程問題（"跨上下文"和"長程任務"意思重複）
OK: 長程任務的跨上下文挑戰

**標題裡保留逗號**：先...再...順序句（先修復評測，再修復 Agent）；對仗列舉（同步決策，非同步 I/O）。

**標題裡逗號改冒號**："主題，副標題說明"這種格式，逗號換冒號更清晰（Prompt Caching，降低重複呼叫成本 → Prompt Caching：降低重複呼叫成本）。

**標題裡去冗餘詞**：「應該如何X」去掉「應該」，直接用「如何X」；副標題如果和主標題意思重疊，合併成一句。
NO: 「Agent 評測應該如何做」 / 「工程實現應該遵循什麼順序」
OK: 「Agent 評測如何做」 / 「工程實現遵循什麼順序」

**標題不要做成名詞並列**: 三個名詞用頓號串起來，沒有觀點，讀者不知道這節想說什麼
NO: 「蒸餾、專用化與持續迭代」 / 「資料、演算法與系統」
OK: 用一句有判斷的陳述：「前沿模型釋出後，訓練鏈路還在繼續跑」
判斷標準：標題能不能單獨成立為一個有意義的句子，能就留，不能就改

**標題要有判斷，不只是名詞**：好標題表明立場或結論，不只是列出主題詞。
NO: 「多 Agent 協作」（只說了主題）
OK: 「多 Agent 協作讓幻覺互相放大」（有判斷）
OK: 「評測先於 Agent，不然你不知道在修什麼」（有立場）

以上是傾向，不是硬規則。判斷式標題適合分析 / 論證型文章；敘事、經歷、探索型長文裡，疑問句和好奇式短語往往更抓人（「機器人怎麼知道自己在哪」「一根沒有銷釘的手指」），同一篇裡兩種可以混用。作者已經定的標題形式優先，別為了「湊判斷」改掉一個好的好奇式標題。

> 逐字元標點（全形 / 半形、破折號、中西空格）由門禁指令碼 `check_punctuation.py` 檢測；下面幾節只保留「什麼時候該破例、引號何時該用」這類判斷，不再逐條機械列舉。

### 引號（""）

引號不是強調鍵。不要因為某個詞"感覺重要"就套上引號。
同理，`「」` 也不要拿來做視覺強調。

NO: 大模型最擅長"翻譯"
NO: 防止 Agent 通過改標準來"提升"分數
NO: Agent 掃了一眼，覺得"差不多了"

OK: 大模型最擅長按規格說明書做對照實現
OK: 防止 Agent 通過改標準來刷分
OK: Agent 掃了一眼覺得差不多，直接宣告完成

引號只用於：直接引述他人說的話、系統輸出內容、錯誤訊息。

### 括號（）

括號裡的內容超過 10 個字，多半說明它該待在正文裡，而不是括號裡。
同一段裡出現 2 處以上括號時，優先把至少 1 處改寫進正文，避免讀感變重。

NO: 傳統 APM（Datadog、New Relic 這類監控延遲和錯誤率的工具）基本幫不上忙
OK: 這類只監控延遲和錯誤率的傳統 APM 基本幫不上忙

NO: 併發的正確用法不是多模型推理，需要併發的是（檔案操作、網路請求、長耗時命令）
OK: 需要併發的是檔案操作、網路請求、長耗時命令，模型推理本身保持單執行緒

可以保留括號的情況：術語首次出現的英文原詞、簡短數值範圍（5~15%）、程式碼引數說明。

### 分號（；）

分號不是懶人句號。兩個放在一起就是因為"感覺有關係"的句子，多半應該直接用句號斷開。

NO: File System State 開銷只有 5~15%，幾乎總是值得的；Verifier Agent 能提升 25~40% 精度，但成本增加 1.5~3 倍
OK: File System State 開銷只有 5~15%，幾乎總是值得的。Verifier Agent 能提升 25~40% 精度，但成本增加 1.5~3 倍

可以保留分號的情況：
- 對仗句：只跑 Layer 2，評分標準會漂移；只靠 Layer 1，根本看不過來
- 列表項分隔：本地 Shell 能處理的；只需靜態知識的；還沒驗證過的
- 中文列舉：一是…；二是…

分號後面接轉折詞是典型錯誤，直接斷句：
> NO: `...也決定後訓練有沒有可以利用的空間；但它沒有決定這個模型會不會聽指令`
> OK: `...也決定後訓練有沒有可以利用的空間。但它不決定模型會不會聽指令`

### AI 味檢測：這幾個模式幫你認味

以下是高頻出現的具體模式（舉例，不完全），用來識別 AI 味，不是必須逐條執行的清單。句子本來自然、清楚就別套規則，命中了味再改。

**1. 昇華句**: 把具體工程觀察上升到普適人生道理
> NO: "很多東西都是這樣，當初成立的假設，過一段時間回頭看可能已經不成立了。"
> OK: 直接給出具體建議，不升華

**2. 對比句式**: AI 最愛的結構，出現頻率高就有問題
> NO: "不是…而是…" / "直覺上…但實際上…" / "X 本身沒有價值，真正有用的是 Y"
> NO: "X 已經不是瓶頸，Y 才是" / "X 不重要，Y 才真正...": "才是/才真正"變體同樣是對比框架
> OK: 直接說結論，不用對比框架鋪墊。"程式碼生成不卡人了，真正費力氣的是評審"比"程式碼生成不再是瓶頸，評審才是"自然得多

**3. 重複核心觀點**: 同一個道理在不同節出現 2-3 次
> NO: 第 0 節說了，第 2 節總結處再說一遍，結語再昇華一遍
> OK: 說一次，後面直接引用或跳過

**3b. 段內重複**: 同一段裡把同一個意思用不同措辭說兩遍
> NO: "沒有約束邊界的 Agent 不是更自由，而是更容易在錯誤路徑上跑很遠都沒人察覺。加約束，是給它一個出了錯還能拉回來的餘地，沒有約束的 Agent 跑偏了都沒人察覺。"（後半句和前半句說的是同一件事）
> OK: 說一遍，夠了。不需要用換一種說法再強調一遍

**4. 引用+解釋句式**: 先拋英文術語/名言，再解釋
> NO: "工程界有句話 'X'，對 Y 同樣如此，..."
> OK: 直接用口語解釋：他們把這個叫 progressive disclosure，就是不要一下全給

**5. 工整並列總結**: 每節結尾必有一句"三層缺一不可"型總結
> NO: "三層缺一不可，只靠 A 沒用，只靠 B 不夠，單獨拿出來都有漏洞。"
> OK: 口語化：用下來感覺，少任何一層都會出問題

**6. 瓶頸轉移句**: 一眼 AI 部落格
> NO: "瓶頸從'X'轉移到了'Y'"
> OK: 直接說新情況：程式碼生成不卡人了，壓力全壓到評審這一側，不用"瓶頸"這個詞

**7. 優先順序結論句**: 聽起來像教條
> NO: "安全邊界要比任何功能都先做好" / "是生產級別必須的"
> OK: 說清楚為什麼：能跑 shell 就能刪庫，安全得先來

**8. 系統性定義開頭**: 教科書格式
> NO: "X 是對 Y 的系統性評估，包括測試用例、評分標準和自動化驗證流水線。"
> OK: 從問題或場景出發，不從定義出發

**9. 完美並列 bold 標題**: 一組"有X，讓Y而不是Z"結構
> NO: 四個 bold 標題全是"**有明確的參照物，讓 Agent 翻譯而不是創造**"這種格式
> OK: 每個點語氣不同，或直接改成散文敘述

**10. 順序/重要性結論**: AI 喜歡用"所以"收尾說教
> NO: "所以順序很重要：評估工具可信，測量結果才有意義。"
> OK: 直接說怎麼做："懷疑 Agent 出了問題，先確認 Eval 沒問題。"

**11. 混雜段落**: 一段塞了多個不相關話題
> NO: 一段裡同時講可觀測性順序、File System State 成本、Verifier Agent 精度、多 Agent 引入時機
> OK: 每段只說一件事，其餘拆到各自對應位置，沒有對應位置的直接刪掉

**12. 章節引介過渡句**: 章節結尾或開頭寫一句引出/承接下一節的橋接句
> NO: 「上面這些模式解決的是控制流怎麼搭，下面再看另一個更工程的問題，系統為什麼能跑穩。」
> NO: 「X 保證了方向對了，執行完還得確認它真的做對了。」← "X 做完了，還有 Y"的機械銜接，只在宣告結構，沒有資訊量
> OK: 直接刪掉，章節標題本身已經承接

**例外：這幾類章節引導是必要的，不要刪：**

- **內容說明**：告訴讀者這節為什麼值得看，有實質資訊量
  > OK: 「這塊很少有教程展開講，但它很影響成本結構和設計取捨。」

- **模式切換訊號**：長文裡從原則轉向案例、從理論轉向實操，讀者需要知道內容性質變了
  > OK: 「前面幾節講的是原則，這一節直接看一個真實專案怎麼落地。」

- **行動指引**：結尾給讀者一個具體的下一步，不是在說文章做了什麼
  > OK: 「想知道自己的配置離這些原則差多遠，跑一次 /health 是最快的方式。」

判斷標準：句子裡有沒有對讀者有用的資訊，有就留，只在宣告文章結構就刪。

**13. 收尾"給你答疑/給你答案"**: 文末或節末用「應該能給你答疑」收尾
> NO: 「下面文章應該能給你這些問題答疑。」
> OK: 省略，或改成：「讀完這篇，這幾個問題應該能有些答案。」

**例外：圖後說明段落不能以"重複"為由刪除**
圖片的 alt text 讀者看不到，圖後的文字說明才是讀者真正看到的解釋。圖後說明段不屬於"收尾總結"，不要刪。
判斷標準：如果刪掉這段文字，讀者就看不懂這張圖，就必須保留。

**14. 段末收尾總結句**: 一段剛解釋完某個機制，結尾再加一句把剛才的意思重述一遍
> NO: "這不只是設計選項，是資源約束的結果": 緊接在已經解釋了具體代價之後
> NO: "模型本身成了訓練流水線裡的工具": 剛解釋完模型在給下一代產出訓練資料
> NO: "主流實驗室基本都在用這類多階段配方了": 四個階段剛剛描述完
> OK: 說完就停，事實本身已經說明一切，不需要再"總結"一遍
> 識別訊號：這類句子往往以"到這裡"、"這說明"、"這本身就是"、"也就是說"、"可以看出"開頭，或者是段落最後一句比其他句短且抽象

**15. 英文術語首次出現後，後續一律用中文**
- 首次出現：保留英文 + 中文註解，或中文前置 + 英文括注（`指令微調（Instruction tuning）`）
- 後續出現：只用中文，不要英文/中文混用
> NO: 第一次"冷啟動 SFT（cold start）"，第五次還在寫"cold start 讓 RL 穩定啟動"
> OK: 第一次解釋清楚，後面一律寫"冷啟動"
- 例外：SFT、RL、MoE 這類已成行業通用縮寫，可以全程保留縮寫形式

**16. 思考過程用了物理動作動詞（翻譯腔套路一）**

接住、擊穿、鋒利、不崩、不爆、打穿、扛住、收緊、落地、推開、撐不住，這類詞把抽象認知過程想像成了物理動作，骨架是英文（catch / pierce / sharp / break / blow up）。

> NO: 「你這幾條我都接住了。」「這個論證被擊穿了。」「更鋒利的重構：」
> OK: 「你這幾條我都收到了。」「這個假設不成立。」「換一種更準的講法：」

自檢方式：寫完一段，把所有動詞圈出來，凡是中文日常不會這樣用的，挨個換掉。

**17. 形容詞預判+冒號引出內容（翻譯腔套路二）**

「更乾淨：」「邏輯很清晰：」「問題很直接：」「結論很明確：」，形容詞搶先下判斷，冒號才引出事實。
問題有三：搶走了讀者自己評估的機會；形容詞幾乎總是多餘的；後面的事實本身就能讓讀者得出那個感受。

> NO: 「驗證得比我預期的更乾淨：上下文不崩、成本不爆、狀態可恢復。」
> OK: 「資料把你的感覺證出來了：上下文不亂、成本壓得住、狀態能恢復。」

改法：直接把形容詞那一節刪掉，只留後半句事實。如果非常想保留那個形容詞，多半說明後面內容沒講清楚，要回頭補內容。

**18. 抽象名詞做主語，形容詞當結論（翻譯腔套路三）**

"X 的 Y 比 Z 更 W"這種骨架，主語是抽象名詞（工程上的現實、這份資料、生態的成熟度），結論是形容詞（難看、直接、漫長），中間系動詞連線。讀完不知道到底哪兒難看、難看在哪個環節。

> NO: 「工程上的現實比這些數字難看。」
> OK: 「這些數字只反映了採用面；真往下看各家怎麼接，早就對不齊了。」

改法：讓人、動作、或具體物件做主語，讓事實自己說話。凡是碰到"X 的 Y 比 Z 更 W"骨架，都應該重寫。

**19. 有穩定中文對譯的英文詞直接混入（翻譯腔套路四）**

context、state、cache、claim 這類詞有現成中文對譯：上下文、狀態、快取、斷言。留著英文原詞讓讀者每次切換都消耗注意力。

> NO: 「context 不崩、成本不爆、state 可恢復、cache 命中率高。」
> OK: 「上下文不會亂、成本壓得住、狀態能恢復、快取命中得上。」

判斷標準：中文技術圈已有通用譯法，就換中文；術語在中文圈還未收斂（如 prompt、embedding、tokenizer），保留英文合理。
例外：SFT、RL、MoE 這類已成行業通用縮寫，全程保留縮寫形式。
常見可替換詞：context→上下文、state→狀態、cache→快取、claim→斷言、runtime→執行時、contract→契約。

**20. 對稱粗體起句**: `**詞語**。……` 連續出現 3 行以上即觸發 AI 模板感。把第 4 個改成行內嵌入式粗體（`句子里加 **重點**`），打破節奏。

**21. 挑戰與未來展望模板段**: "儘管面臨挑戰，X 憑藉 Y 仍將持續蓬勃發展，成為 Z 不可或缺的一部分。" 是 AI 最愛的收尾套路。
> NO: "儘管面臨挑戰，X 憑藉 Y 仍將持續蓬勃發展，成為 Z 不可或缺的一部分。"
> OK: 直接說具體的挑戰和具體的應對，不要"儘管…仍…"+"未來展望"的套路收尾。

**22. 同義詞迴圈**: 同一段裡把同一物件用 3 種以上同義詞替換，是 AI 重複懲罰機制的副產物。
> NO: "主人公面臨挑戰。主角必須克服困難。中心人物最終獲勝。英雄回到家中。"
> OK: 選一個稱呼用到底。"主人公面臨挑戰，最終獲勝回到家中。"

**23. 虛假範圍**: "從 X 到 Y" 結構裡 X 和 Y 不在同一尺度上，假裝覆蓋全光譜。
> NO: "從大爆炸的奇點到暗物質的神秘舞蹈"（不是同一類物件）
> NO: "從架構設計到團隊文化"（跨域強湊）
> OK: 直接列出真正涵蓋的兩三件具體事，或者只挑一件展開。

**24. 知識截止日期免責宣告殘留**: AI 關於"截至 X 時間 / 根據可用資訊 / 現成資料中沒有廣泛記錄"的免責宣告被原樣貼上到正文。
> NO: "雖然關於公司成立的具體細節在現成資料中沒有廣泛記錄，但它似乎是在 90 年代的某個時候成立的。"
> OK: 要麼查清楚直接寫"成立於 1994 年"，要麼不要寫這一句。模糊免責宣告本身就是 AI 痕跡，要刪乾淨。
> 注: 與「時效性事實加邊界詞」不同，那條是作者主動加邊界（"截至 2026-04 我看到的是…"）；這條是 AI 自動生成的甩鍋式免責。

**因果/結論語氣要像歸納，不像定論**
技術文章裡，判斷方向沒問題，但懂行讀者看到”換來的是/就是從這裡來的/是X的路徑”這種語氣，容易挑刺。改成歸納語氣：

> NO: “換來的是同等引數下更高的能力密度” / “效能差距就是從這裡來的” / “也是能力解耦的路徑”
> OK: “公開結果顯示，這類配方通常能換來更高的能力密度” / “從公開結果來看，差距通常是可觀測的” / “一個關鍵原因是能力解耦”

**術語列表需要”為什麼值得記”的錨**
一段裡列出多個專有名詞（muP、WSD lr、batch size 等）而不解釋為什麼讀者該記住，更像點名單不像論證。加一句：

> NO: “這些都開始出現在正式訓練報告裡。能看出來的一條線是，配方越來越細。”（只說存在）
> OK: “這些細節之所以值得記，是因為它們正在成為同規模模型之間拉開差距的地方。”（說明為什麼重要）

**長段落拆分標準**
一段超過 400 字、或塞了 3 個以上獨立概念，移動端讀起來會累，也容易沖淡最重要的那一句。拆分點：概念切換處加空行，不要因為”都屬於同一主題”就塞在一起。

**案例引入需要半句”為什麼選它”**
直接 zoom in 到具體案例（PARL、DeepSeek-V3 等）時，如果切換感突然，先加半句說明它代表哪條路線或設計選擇，再展開細節。

> NO: “Kimi K2.5 的 PARL 是這裡最值得拆開的工程案例。它只訓練 orchestrator...”（直接進細節）
> OK: “Kimi K2.5 的 PARL 代表了一條新路線：只訓 orchestrator、把 credit assignment 收到編排層。獎勵訊號分三類...”（先說代表什麼）

### 工程技術文實戰規則

下面這組來自真實改稿回合，優先順序高於”風格偏好”：

- 刪段之前先確認資訊量。刪除整段（不是單句）之前，確認這段沒有在別處重複的技術事實、資料或邏輯。”刪掉段末總結句”的規則針對結構性重複，不適用於展開新資訊的段落。如果不確定，改成提議而不是直接刪。
- 先保語義，再去 AI 味。為了”更口語”改壞原意，屬於失敗改寫
- 括號和引號預設少用，但術語首次出現、歧義消解時要保留，不要為刪符號犧牲清晰度
- 句號密度要控。連續短句太多會像彙報提綱，適當合併成複句
- 避免“訓人式”表達：反問、命令、質問式開頭都容易讓讀者產生被指導感
- 避免抽象判詞堆疊，優先寫可觀察事實、鏈路位置和具體影響
- 結論不重複宣告。第 0 節說過的核心判斷，後文不要再換措辭重複一遍
- 保留作者的內在矛盾。如果原文在不同段落持有看似矛盾的立場（比如既推崇自由又強調紀律），不要替作者消解。時間性矛盾（早期 vs 近期觀點）標註演化即可；領域性矛盾（工作 vs 生活的不同規則）保留兩面；本質性張力（價值觀的內在衝突）原樣呈現，這通常是文章最有深度的部分

### Summary 寫法

`summary` 先判斷目標，不同目標寫法不同：

- 導讀型：告訴讀者“這篇會講什麼”，不提前講完整結論
- 總結型：概括“這篇講了什麼 + 得出什麼結論”

實操規則：

- 導讀型用“這篇會從 A 講到 B，重點看 C”
- 總結型用“這篇從 A 到 B，最後看到 C”
- 不要混寫，避免一段裡既像導讀又像結論宣判
- 預設 2 到 3 句，資訊完整但不鋪滿正文細節

### 高頻替換：報告腔和不喜歡的表達

按「左邊少用，右邊推薦」執行，讀起來有同樣報告腔或不自然的一律適用。

| NO | OK |
|----|----|
| 主要敘事 | 大家通常用...來解釋... |
| 系統梳理 | 從...一路講到... |
| 核心結論是 | 最後會看到 |
| 邏輯分工 / 流程節點 | 為了看分工 / 更細的版本 |
| 公開口徑裡 | 按公開資料 |
| 共同模式已經很穩定 | 能看到幾個共同點 |
| 可以從三個角度看 | 可以先看三件事 |
| 不需要讀成 X | 不只是 X |
| 別掉鏈子 / 露過頭（過重口語）| 直接說事實 |
| 團隊 / 實驗室 / 行業（抽象主語）| 能寫動作就別先擺抽象主體 |
| 真拆開看 / 這背後是同一個變化 / 真正的問題變成了 / 真正關鍵的問題是 / 都在說明同一件事（講解腔起手）| 直接說 |
| 先問問是不是 / 你要先明白 / 先搞清楚再說（訓人感起手）| 可以先看 / 先確認 |
| 硬約束（工程黑話）| 約束 |
| 擺出來（半口語半講稿）| 直接陳述 |
| 當然 / 這話不算錯，但 / 這麼理解不能說錯，但（讓步腔）| 直接說結論，不先讓步再轉折 |
| 塑形 / 塑造（行為、方向、結果）| 調整 / 決定 / 影響 / 最佳化 |
| 相鄰（空間詞描述邏輯關係）| 關係緊密 / 有交集 |
| 聚焦（空泛目標詞）| 重點寫什麼 / 主要看什麼 |

補充：比較表達優先自然中文，`最清晰` 通常比 `最清楚` 更穩；避免「句子評價句」，「這句話解釋不了」直接寫成「X 解釋不了 Y」。

### 參考資料排列

- 預設用單列表，不強制按“論文/部落格/倉庫”分類
- 排序按承重程度，不按發表時間
- 論文和官方技術報告優先，倉庫與部落格只保留高承重項
- 數量以可讀為先，通常 10 到 14 條比較穩

### 文章自說明句（預設少寫）

文章不該反覆談自己在做什麼。預設直接進內容，必要時只保留 1 句路線提示。

NO: `先給最短結論，就四句：`
NO: `這篇真正想釘住的，就是這件事：`
NO: `如果先只記一張表，可以先記住這六層：`
NO: `腦子裡還是那老三樣：X、Y、Z`（代替讀者做歸納）
NO: `最常見的解釋就是三件事：`（同上）
NO: `拿一組具體數字看會更直觀。`（宣告資料要來了）
NO: `如果說...那...`（條件句引入段落）
NO: `這篇文章接下來會從 X 講到 Y。`（同上）

OK: 直接進結論、進數字、進內容。結構交給標題和邏輯順序，不要靠過渡句反覆宣告。
OK: 如果確實需要路線提示，只寫一遍，避免在開頭和結尾重複。

### 術語註解不要扎堆

多個術語同時首次出現時，括號註解會堆在一起，讀起來很重。處理方式：

- 把註解融入行文：`GRPO（組相對策略最佳化），而不是傳統 PPO（近端策略最佳化）` → `這裡的關鍵選擇是 GRPO 而不是傳統的 PPO`，註解分散到後文
- 把首次介紹提前：在自然引出術語的地方加註，而不是在密集使用的地方一次性堆上去
- 如果上下文已經說清楚了意思，括號註解可以完全省略

### 圖片引導語

圖片前的說明句不用「下圖」，用「這張圖」或「下面這張圖」，避免每句都一樣。

### 圖片節奏

帶圖技術長文裡，圖片放哪兒決定整段讀起來順不順。三條經驗：

**圖當 TL;DR，列表/表格當詳情**。圖片放在「intro 一句話 + 圖 + 列表」這個位置最舒服。把圖丟在列表/表格末尾、緊貼下一個 `---` 的位置看著空，上面是序號 + 加粗也很醜。

**圖片 alt 要和正文 prose 對齊**。如果 alt 列了 6 項保號清單、prose 改成 5 項，要麼改 alt、要麼重畫圖，不能讓兩者錯位。讀者掃到的是圖視覺 + 正文文字，alt 給搜尋引擎和無障礙。

**段末"為了平衡而加圖"是 AI 模板**。圖不是裝飾節奏的工具。如果某段沒自然想到畫什麼，就別湊圖，文字密就讓它密。

### 技術文章額外規則

**事實與可驗證性優先於去 AI 味**
技術文章先保準確、清楚、可驗證，再追求自然。不要為了刪 AI 味，把版本、環境、依賴、出處、復現條件、風險邊界刪掉。如果原文缺這些資訊，不要編，可以保留問題或收斂語氣。

- 版本、平台、依賴會影響結論時，要保留或補全對應上下文
- 引用“官方建議”“文件說明”“測試表明”時，要有具體出處；沒有出處就不要寫成定論
- 命令、配置、程式碼不要只貼結果，要解釋關鍵引數、關鍵路徑和為什麼這麼改
- 效能、安全、穩定性結論要說明觀察口徑，比如資料來源、測試環境、樣本範圍
- 個人經驗、單次排障、區域性實驗不能寫成通用規律
- 寫方案時順手補一句邊界：什麼時候適用，什麼時候別這麼用

**時效性事實加邊界詞**
價格、訂閱檔位、版本號、產品名、隱藏命令、釋出時間這類容易過時的事實，加邊界詞寫：「截至 2026-04」、「我這裡看到的是」、「以當時顯示為準」、「目前」。讀者過兩個月對著失效資訊照搬時，能立刻看到這是哪一時刻的截圖。

**專有名詞改前 verify**
字型名（滄耳 / 倉耳 / 蒼耳）、品牌名、書名、人名、產品名改之前先 grep 或查官網，不憑印象。事實類改動比風格類改動風險高，反而最容易拍腦袋下手。

**開頭不要放背景鋪墊段落在最前**，比如"國內現在也有不少打著 X 旗號的產品..."這種定性背景，放到正文具體位置更自然，不要作為全文開場白。

**技術術語解釋不用分號並列**
> NO: "系統提示的三層結構：身份定義，常駐、輕量；約束規則，常駐、精確；領域知識，按需載入。"
> OK: 直接說："系統提示分三層：身份和約束規則常駐，領域知識按需載入。"

**場景描述代替核心問題格式**
> NO: "這類系統要解決的核心問題是：Agent 常駐伺服器，同時需要..."
> OK: "場景是：Agent 常駐伺服器，要同時接多個渠道的訊息..."

**資料後不要加 AI 營銷腔結論**
> NO: "token 節省 37%，消除 19+ 次無效推理。"
> OK: "token 從 15 萬降到 2000，中間 19+ 次來回推理也省掉了。"

**幻覺/錯誤原因不用學術解釋框架**
> NO: "原因在於 LLM 的中立性偏向。以'幫助、誠實、無害'為目標訓練出來的模型，在群體討論中天然傾向服從..."
> OK: 直接說現象："LLM 訓練目標是'幫助、誠實、無害'，在群體裡就會傾向不反對多數人。一個說錯了，後面的順著走。"

**不要用外來術語/模型名做比喻，除非讀者肯定知道**
> NO: "這就是瑞士乳酪模型的現實：每一層都有漏洞"
> OK: "每一層都有盲區，疊在一起才夠用"

西方管理學模型名（瑞士乳酪模型、長尾定律等）、外語品質管理術語（Poka-yoke）在中文技術文章裡多數人看不懂，去掉名字，直接說清楚那個道理就行。

**多方案例並列時合併敘述，不要各自單獨成段**
同一個技術觀察涉及 3 家公司/方案時，合併成一段，每家貢獻一句話，讀起來像分析而不是列表。
> NO: 三段分別講 Kimi、Cursor、Chroma 的做法，每段獨立成段
> OK: "三家承擔的重點也很清楚。Kimi 用 PARL 解決...，Cursor 用 self-summarization...，Chroma 則把 prune_chunks 訓成策略本身..."

**有名字的來源自然融入句子，不要做括號註釋或單獨引用句**
> NO: （根據 Philipp Schmid 的分析）今天 agentic model 報告共同模式已經很穩定
> NO: 根據 Philipp Schmid 的研究，今天 agentic model 報告共同模式已經很穩定。
> OK: "把 Philipp Schmid 對 Kimi、Cursor、Chroma 的歸納放在一起看，能看到幾個共同點。"

### 技術文章自檢

交付前快速掃一遍，優先看這些問題：

- 這篇文章到底解決哪個具體問題
- 版本、環境、依賴、上下文是否足夠讀者復現
- 每段是否都有新資訊，還是隻是在換說法總結
- 程式碼、命令、配置是否解釋了關鍵部分
- 結論有沒有對應的證據、資料或來源
- 有沒有只講收益，不講代價、風險和邊界
- 有沒有把個人經驗寫成所有場景都成立

### Polish 後期殘留 checklist（10+ 輪之後用）

風格級 AI 味清乾淨後，還有一類「句子級殘留」最容易被漏掉。每輪 polish 末尾按這 6 類掃一遍：

**1. 疊詞拗口**：同一句裡出現兩個意思接近的詞（"也能上手用"、"也都"、"也是另外"）。識別：把句子拆成最小動作主謂賓，看哪個修飾是冗餘的。

**2. 缺逗號長句**：超過 25 字的句子裡沒有逗號斷點，多半在某個時間狀語 / 條件狀語後漏了「，」。識別：朗讀時想換氣的位置就是該加逗號的位置。

**3. 中英術語一致性**：同一篇裡同一個常用詞（copy / 複製、context / 上下文、setting / 設定）反覆切換形態。識別：搜文中所有英文 token，看是否有對應中文已成主流，主流就統一為中文。

**4. 突然出現的比喻 / 概念**：作者自己腦子裡有的比喻（"工作台"、"水位"、"賬本"）沒在前文鋪墊就直接用。識別：第一次出現的非通用比喻詞，前一段必須有鋪墊，沒有就換通用詞。

**5. 「上 / 下 / 裡」字殘留**：「方案上都」「思路里」「概念上」這類介詞殘留是早期草稿的痕跡，刪掉不影響意思。識別：搜「上都」「裡都」「上的時候」。

**6. 缺關鍵修飾**：某個名詞第一次出現需要修飾才能區分性質（"Anthropic 官方推出的 Claude Design" vs "Claude Design"），漏了讀者會和上下文混淆。識別：每個產品 / 工具名第一次出現，問一句"讀者能否區分這是誰家的、跟前文工具的關係"。

判斷標準：1-3 類是字元級、5 分鐘掃完；4-6 類要帶上下文判斷、需要全文回讀。10 輪後 prose 大改不動了，時間就花在這 6 類殘留上。

### 專家腔

潤色容易把作者改得比原文更像專家、更會教人。下面這幾處是同一個傾向的常見表現。

**0. 實作經歷不能為了工程感補細節**
> NO: 作者只說"序列埠通訊難"，潤色時補成"ACK 丟了、超時重傳、翻序列埠日誌定位"這類原文沒有的排障故事
> NO: 同樣地，原文只說"序列埠通訊難"，不要替它補出"波特率、指令格式、模組狀態"等原文沒提的具體引數
> OK: 只順句、不加事實，原文給什麼寫什麼：「序列埠通訊我反覆試了好多次才弄對，差一點就放棄了」
> 判斷：硬體型號、協議欄位、波特率/指令格式等引數、日誌結論、故障原因、排查順序，只要原文或使用者沒給，就不要補。原文若已寫明這些引數，可以保留並順句，但不要再往上疊新的故障細節。技術文的人味來自真實細節，不來自替作者編一個更像工程師的 Debug 故事。

**1. 元敘事 in 正文**（跟"文章自說明句"是 PRE-meta，這條是 IN-BODY meta about article-writing itself）
> NO: 「寫到這裡」「寫文章時」「更穩的寫法是」「我把 X 單獨拿出來講」「這裡要小心一個說法」放在正文裡
> OK: 直接陳述，或換成「一圈下來」「更準確的說法是」這種不帶"寫"字的銜接
> 例外：末尾 italic publishing note 可以用「本文完成於 X」這種 convention

**2. 二人稱讀者預測**（跟"訓人感起手"是命令式，這條是預言式）
> NO: 「你會自然地問」「你會知道 X」「你會同時多出 X」「你會發現」
> OK: 去"你"做主語，事實陳述：「翻論文時會先看 X」「同時會多出 X」「自然會想問 X」

**3. 段首 announce-a-feature 引子**（rule 12 章節引介過渡句的段內變體）
> NO: 「X 也是容易被低估的部分：」「X 也是 Y 的延伸：」「還有一項 Y 經常被低估：」「我瞭解到 X 常見的 Y 有這幾類，工程代價也各不一樣：」
> OK: 直接進 X：「X 也容易被低估：[直接講]」「再往後一層是 X：[直接講]」，分類引子直接進列表或表格

**4. 章節編號一/二/三 prefix**
> NO: `## 一、X` `## 二、Y` 中文數字編號像教材目錄
> OK: 去字首，標題留描述/判斷
> 例外：參考文獻、操作步驟、明確有順序的列表可保留 1./2./3.

**5. 同對比框架反覆使用**（rule 2 對比句式 + rule 3 重複核心觀點的交叉地帶）
> NO: 「X 只是表層，更有用的是 Y」「X 只是表面，Y 才說明價值」「X 只是開頭，Y 才是…」同一文章 2+ 次
> OK: 留一個正典例項，其餘 vary 骨架（「看 X 能不能 Y」/「X 是表面，能不能 Y 才說明價值」）

**6. 形容詞 announce-claim 不帶列表**（擴 rule 17，rule 17 收的是 `形容詞：[列表]` 這種）
> NO: 「原因很樸素」「X 很現實」「代表很現實的優勢」「展示了很強的運動效能」（中間陳述，不是列表前）
> OK: 刪形容詞，直接給事實：「原因很簡單：[事實]」「H1 運動效能也很強」「國內挺實在的兩個優勢」

**7. "X 在於 Y / 價值在於 Z" 名詞化 claim 公式**（跟 rule 18 抽象名詞主語相近，這條是"X 在於 Y"系動詞結構）
> NO: 「減少 X 損耗」「價值在於 Y」「吸引力是 Z」「區別在於 W」「關鍵在於 V」
> OK: 動詞化 + 主語具體化：「省掉 X 的麻煩」「最大的好處是 Y」「跟 W 不一樣的是…」

**8. bullet 跑成"純記錄" → 第一人稱敘事，但只用已給細節**（擴列表去 list 化策略）
> NO: bullet 全是 passive 陳述（「X 是 Y / X 燒過 / X 不夠硬 / X 必須自己寫」），讀起來像故障報告
> OK: 轉 prose 段，優先用原文已有的動作和狀態：「踩坑 / 老老實實 / 晃 / 不太對勁 / 最難的是 / 我」
> 例：bullet「OLED 帶電插拔燒過一次，後來所有接線都先斷電」→ prose「OLED 我帶電插拔燒過一次，之後所有接線都老老實實先斷電」
> 風險：不要為了讓段落更"工程師"而補協議、日誌、ACK、重傳、供電、接觸不良等未經確認的排障細節。

**9. 緊鄰 2 段 setup→continuation 用逗號 fuse 成一段**（跨段落版的"句號密度要控"）
> NO: 緊鄰兩段，前段鋪墊、後段承接，中間用段落 break + 句號
> OK: 去段落 break，改逗號融合
> 例：「它都不知道。它跑通的是…」→「它都不知道，它跑通的是…」
> 判斷：後段是 elaboration、example、follow-up 時合；topic 切換時不合

**10. 第一人稱 anchor 的邊界**
> 實作經歷、開頭動機、踩坑過程可以保留「我」；技術判斷、產業分析、表格列名和結論段儘量讓事實做主語。
> NO: 一篇 7 章長文裡反覆出現「我會先看」「我更在意」「我盯」「我不會把」「我自己看一家公司」
> OK: 「動作空間、控制頻率和真機測試比引數量更早決定可比性」「公司層面的差異，最後會變成幾個問題」
> 判斷：第一人稱是經歷證據，不是審稿姿態。中後段如果像作者站出來教讀者怎麼看，優先刪主語或改成可觀察事實。

**11. 學習路徑不要改成入門教程**
> NO: 「入門不用一上來」「先把 X 跑通」「再往前一步」「幾個常見坑」「這一圈下來，我先把收穫留成檢查項」
> OK: 「按我現在的理解，資料大概能這樣串起來」「跑過一遍後，哪些詞會落到具體欄位上」「還有幾個問題我現在沒答案」
> 判斷：原文如果是工程師邊做邊學、把材料慢慢串起來的過程，不要改成老師給讀者安排課程。學習路徑可以寫，但語氣要像作者自己的探索路線。除非使用者明確要教程，少用命令、清單、檢查項、常見坑、入門教程這類框架詞。

**12. 不要把輕一點的作者口氣修成老派說教**
> NO: 「盯」「檢查項」「安全動作放前面」「失敗樣本要不要留」「更有抓手」「後續繼續跟蹤」「需要重點關注」
> OK: 「看」「幾個判斷更具體」「限角度、限速度、急停這些東西要留在本地」「失敗資料怎麼處理」「會落到更具體的問題上」「我現在還沒有答案」
> 判斷：這些詞本身未必錯，但在部落格裡容易變成老派專家指導讀者。作者原本如果是「我跑過 / 我看到 / 我還沒答案」的探索口氣，不要潤成「我來告訴你該怎麼做」。

### 對外發文專項檢查

公開發文（release notes、推文、部落格、newsletter）交出去之前，額外掃三件事：

**1. 身份和敏感訊號脫敏**

公開文章裡不出現可反推作者身份的細節：僱主、地點、具體團隊背景、履歷式表述。技術決策可以具體，身份資訊預設刪。

> NO: "作為在 X 公司做過大型系統的工程師，我發現..."
> NO: "住在北京三年，接觸了很多本地開發者，感受是..."
> OK: "用下來感覺，這套方案在中小規模場景最穩。"
> OK: 直接講技術選擇和依據，不交代履歷背景

**2. 不踩競品**

介紹自己產品時不主動貶低同類產品。功能不如別人的地方可以不提，不要拿來做反襯。

> NO: "Cursor 那種全域性索引很吃資源，我們沒走這條路。"
> NO: "不像 Typora，我們做的時候 X 問題想清楚了。"
> OK: "我們的選擇是隻索引開啟的檔案，不做全域性掃描。"
> OK: 直接說自己做了什麼、為什麼，競品不用出現

**3. 使用者感受先於功能清單**

release notes 和推文裡不要開場就列功能。先給一句場景或感受，再進改動細節。

> NO: "V1.2.0: 新增 X 功能，修復 Y 問題，最佳化 Z 效能。"
> OK: "改了兩處之前用起來總覺得彆扭的地方。一是..."
